# Changelog — Repository Cleanup, Data Architecture & Resend Notifications

This entry covers the audit-and-fix pass described in the cleanup brief.
Grouped by area; see [ARCHITECTURE.md](./ARCHITECTURE.md),
[DATABASE.md](./DATABASE.md), [FORECASTING.md](./FORECASTING.md) and
[ALERTS.md](./ALERTS.md) for the full write-ups behind each change.

## Resend email notifications (top priority)

**Added:**
- `supabase/functions/send-alert-email/index.ts` — Deno Edge Function; the
  only place `RESEND_API_KEY` is read. Checks `notification_preferences`,
  then checks `notifications` for a prior `sent` row with the same
  `alert_id` + `alert_fingerprint` (duplicate guard), then calls Resend,
  then logs the outcome.
- `supabase/migrations/0002_notifications_and_currency.sql` — adds
  `notifications`, `notification_preferences` tables and
  `rental_contracts.currency`.
- `src/lib/email/notify.ts` — client-side dispatch (`dispatchAlertEmail`,
  `dispatchOptimizationRecommendationEmail`), invokes the Edge Function via
  `supabase.functions.invoke`, never touches the Resend key.
- `src/hooks/useAlertEmailDispatch.ts` — mounted once in `Shell`; watches
  the shared alert engine and fires eligible, deduplicated emails for
  staff users.
- `src/services/notifications.ts` — reads/writes `notification_preferences`.
- `src/components/alerts/NotificationPreferences.tsx` — the ON/OFF
  preference panel, wired into the notification bell's gear icon.

**Security:** `RESEND_API_KEY` is a Supabase secret
(`supabase secrets set`), never a `VITE_`-prefixed variable — see
`.env.example`. No frontend code path can read it.

**Spam protection:** two layers — a `sessionStorage`-backed client guard
(cheap, avoids the network round-trip) and the authoritative server-side
check against `notifications` (delivery_status = 'sent'). Alert
fingerprints are bucketed (e.g. overdue days ÷ 7) so a still-open condition
re-notifies on a defined cadence instead of never again or every render.

## Repository cleanup

**Removed:**
- `download-images.mjs`, `search-wikimedia.mjs` — one-off image-sourcing
  scripts used once to populate `public/equipment/`; not referenced by any
  npm script or app code.
- `src/components/SiteMap.tsx` — unused; superseded by `LeafletMap.tsx`
  (zero imports anywhere in the codebase).
- `.vercel/` — build output, untracked from git and added to `.gitignore`
  (regenerated by `vercel build`/`vercel deploy`, should never be committed).

**Dependencies removed** (verified zero imports anywhere in `src/`):
`zod`, `date-fns`, `@hookform/resolvers`.

**Kept, deliberately:** the full `src/components/ui/` shadcn primitive set,
even where a given component (e.g. `calendar`, `carousel`, `sidebar`) isn't
used by any screen yet. This is the design-system kit `components.json`
expects `npx shadcn add` to extend — tree-shaken out of the production
bundle when unused, and not "dead code" in the sense the brief asks to
remove.

## Folder restructure

`src/components/` was a flat list of 23 top-level files; reorganized into:

```
components/
├── common/    (Shell, Panel, Table, CommandPalette, NotificationCenter,
│               ActionSheet, AIAssistantModal, InsightCard)
├── auth/      (AuthModal)
├── fleet/     (EquipmentHero, LeafletMap, Gantt, AssetInspector,
│               SiteInspector, CameraQRScanner)
├── rental/    (NewRentalModal, RentalOperationsCenter, ApprovalCenter,
│               DepositManager, CustomerPortal)
├── inspection/(InspectionComparisonModal)
├── alerts/    (NotificationPreferences)
└── ui/        (unchanged — shadcn kit, path pinned by components.json)
```

New top-level directories:
- `src/types/fleet.ts` — domain types, extracted out of `data/fleet.ts` so
  `services/`/`lib/` can import them without importing the stateful store.
  `data/fleet.ts` re-exports them, so no existing `from "@/data/fleet"`
  import broke.
- `src/services/` — `rentals.ts`, `notifications.ts` (Supabase writes).
- `src/lib/supabase/` — moved from `src/lib/supabase.ts` (nothing imported
  it yet, so this was a zero-risk move).
- `src/lib/alerts/`, `src/lib/forecast/`, `src/lib/email/` — the three
  single-source-of-truth engines plus the email dispatcher.
- `src/lib/demoClock.ts` — the shared `DEMO_TODAY` anchor (see below).
- `src/hooks/useAlertEmailDispatch.ts`.

`src/data/fleet.ts` itself was **not** moved/renamed — every screen imports
it and a rename would have touched ~15 files for no functional benefit;
its role (in-memory store, not "data") is now documented inline and in
ARCHITECTURE.md instead.

All ~40 import paths affected by the moves were updated in the same pass;
`npm run build` and `tsc --noEmit` both pass clean afterward.

## Check-In/Out rental amount (section 4/5)

- `RentalContract` gained a `currency` field (defaults `"INR"`); the
  amount/deposit fields it already had (`monthlyRentalRate`,
  `securityDepositAmount`) are reused, not duplicated — matching the
  schema's existing `rental_contracts` columns.
- `createRentalContract()` in `data/fleet.ts` now accepts optional
  `monthlyRentalRate`/`securityDepositAmount` overrides instead of always
  deriving them from the asset's list rate.
- `NewRentalModal.tsx`: rental staff now get editable amount/deposit
  number inputs (customers still see the quoted, read-only price) —
  different rentals of the same or different equipment can carry different
  amounts, and the value entered is what gets saved and displayed
  everywhere downstream (`check.tsx`, `DepositManager`, `RentalOperationsCenter`,
  `CustomerPortal`).
- Every rental-lifecycle mutation (`createRentalContract`, `approveCheckOut`,
  `approveCheckIn`, `approveDepositRefund`, `addAuditLog`) now also writes
  to Supabase via `src/services/rentals.ts` (fire-and-forget, no-ops
  without a configured project) — see DATABASE.md for the exact table
  writes.
- Security deposit refund math (`held − approvedDeduction = refund`) was
  already correctly separated from rental revenue in the UI
  (`InspectionComparisonModal.tsx`) prior to this pass; it now also
  persists to the `security_deposits` table.

## Alerts consolidation (section 13-15)

- New `src/lib/alerts/engine.ts` — the one `buildAlerts()` implementation.
- `routes/alerts.tsx`, `components/common/NotificationCenter.tsx`,
  `routes/anomalies.tsx`, and `data/fleet.ts:summary()` were all rewired
  to call it instead of each maintaining separate rules.
- `routes/anomalies.tsx` no longer reads the static `Asset.anomalies` seed
  strings for detection — it filters the shared engine's `type === "anomaly"`
  alerts, which are computed live from telemetry. `Asset.anomalies` is kept
  on the type (marked `@deprecated` for alerting) only because the asset
  history narrative still references it.
- New `src/lib/demoClock.ts` exports `DEMO_TODAY`, now the single anchor
  used by the alert engine, `data/fleet.ts:isOverdue`, and the Gantt "today"
  marker — previously the alert engine (new) defaulted to the real
  `new Date()` while the rest of the app used a fixed 2025-05-10 anchor,
  which would have reintroduced the exact inconsistency this pass fixes.
- **Found and fixed a real instance of the "5 vs 3 Overdue" bug** section
  15 warns about: `checkIn < today && status !== 'Idle'` was independently
  re-derived in three places (`alerts.tsx`'s old `buildAlerts`, the Gantt
  chart, `fleet.ts`'s old `isOverdue`) and incorrectly flagged three
  healthy, still-`Active` rentals (EQX1003, EQX1005, EQX1006 — whose
  original expected-return date had passed while the rental was simply
  extended) as overdue, on top of the one asset genuinely in that state
  (EQX1002). `RentalOperationsCenter`'s KPI card used a different, correct
  rule (`status === "Overdue"`) the whole time, so it alone showed the
  right count — the Alert Command Center, notification bell, dashboard
  status bar, and Gantt chart all overcounted. Fixed by making
  `status === "Overdue"` (already the authoritative field every status
  pill reads) the single overdue rule, used everywhere; verified via SSR
  smoke test that `/alerts` now shows exactly the one genuinely overdue
  unit.

## Migration instructions (for a real Supabase project)

1. `supabase db push` (or run `schema.sql` then `migrations/0002_*.sql`
   manually) against the target project.
2. `supabase functions deploy send-alert-email`.
3. `supabase secrets set RESEND_API_KEY=... RESEND_FROM_ADDRESS="Smart Rental <alerts@yourdomain>" PUBLIC_APP_URL=https://your-app-url`.
4. Set `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` in the app's build
   environment (Vercel/hosting provider env vars, or `.env.local` for
   local dev).
5. Everything in `services/rentals.ts` and `services/notifications.ts`
   activates automatically once `isSupabaseConfigured` is true — no code
   change required.
